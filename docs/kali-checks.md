# Checks to run by hand on Kali

CI's `kali` job covers 28 of these 60 steps, some of them in part (three of them, the layout, the one note window and its closing at `finish`, are new and have not run in CI yet), in the official Kali image (`kalilinux/kali-rolling`) on every run of the workflow: as root, in a container, with the release file installed while the container's network is off (it is connected again for the cycle), with a virtual display and `xterm` standing in for the desktop, the container's gateway as the target, an OpenVPN file with no server behind it, and two small test packages for the tools: one with a shell script for its command, and one Python tool on a test runtime package that carries the pinned upstream CPython 3.13 build. The job is in `.github/workflows/ci.yml` and its driver in `.github/scripts/kali-cycle.py`. Each step below says what the job covers, after **Kali job:**, and what still needs a person at a real Kali desktop, after **By hand:**. A person is still needed for the real terminal emulator and focus behaviour, a Hack The Box tunnel, Kali's Ctrl-P prompt toggle, and everything as a normal user with `sudo`.

Run the unit tests first (this needs `python3-venv` and `git`, `apt install python3-venv git`; installing the app does not): `python3 -m venv .venv && .venv/bin/pip install -e ".[dev]" && .venv/bin/python -m pytest`. Kali's own `python3` is enough for this, and is not the Python the installed app runs on. The tests that skip on Windows because they need Linux (symlinks, named pipes, file modes, ownership, inodes, `/proc`, signals, the installer, virtual environments, the recorded shell's startup files) run there. The three tests of the real asciinema skip unless `PWN_BROKER_REAL_ASCIINEMA` names the pinned binary: after the install below, run them with `PWN_BROKER_REAL_ASCIINEMA=/opt/pwn-broker/app/bin/asciinema .venv/bin/python -m pytest tests/test_record_real.py`. All three should pass, as they do in CI. **Kali job:** the whole suite as root on Kali's own Python, with the real asciinema from the installed release file, the three tests of it included. **By hand:** as a normal user.

Then install a release file and work one box end to end. Use the one from the release page, with the install line in the README, or build one from a checkout on x86_64 Linux (`.venv/bin/python release/build.py`, see CONTRIBUTING.md) and run `sh install.sh --from dist/pwn-broker-<version>-linux-x86_64.tar.gz`. Open a new terminal and start. Do the list once as root and once as a normal user. **Kali job:** the root run, with the steps marked below, on the app's bundled Python. **By hand:** the normal user run, and the install's `sudo` step.

- [ ] `x-terminal-emulator -e vim -u ...` opens the note window. If the option is not `-e`, add the right form to `open_note`. **Kali job:** covered under the virtual display, where `x-terminal-emulator` is `lxterm`, Debian's wrapper around xterm. **By hand:** with the terminal a Kali desktop opens by default.
- [ ] The launch opens with `pwn-broker <version>` and a blank line. The menu is under `Boxes`, and a new box's questions under `New box` and `Target 1`. Every line is indented two spaces but these, which are flush left: the prompt line, the launch header, the headings, `setup`'s lines, `vpn log`'s lines, `--help`, `--version` and `record --help`, and the output of `cred show` and `path`. There is one blank line around each command's output and each yes or no question, never two. **Kali job:** the header, the `New box`, `Target 1` and `New credential` headings, and the indent of every line it waits for. **By hand:** the menu, and the blank lines.
- [ ] With the note open, `note` prints `ok    the note is already open` and starts no second vim (`pgrep -a vim` shows one for the box). `quit`, then `pwn-broker resume` with the note still open: the same line, and still one vim. **Kali job:** one vim after the new box and after `import`, and `ok    the note is already open` with that same vim when the box is opened again. **By hand:** `note`, and the terminal a Kali desktop opens by default.
- [ ] `finish`, and `y` at `remove working folder?`: afterwards neither the note's vim nor its terminal window is left. Again with a line added to the note and saved before answering `remove working folder?`: the folder is kept, with `warn  the note changed after the archive was made; the folder was kept`. **Kali job:** neither the vim nor its `xterm` is left after each `finish`. **By hand:** the terminal a Kali desktop opens by default, and the kept folder.
- [ ] Finish a box and remove its folder, then start a new box with the same name on the same day: its folder and its archives end in `-2`, and its `finish` does not ask `replace the existing archive?`. **By hand.**
- [ ] At a yes or no question, `2` and `maybe` get `fail  answer y or n` and the question again; `y`, `Y`, `yes`, `n`, `no` and Enter are taken. **By hand.**
- [ ] `exit` asks the export question and leaves, as `quit` does, and `clear` clears the screen. `target rename a b` prints `fail  too many arguments: b` with `usage: target rename <target>` under it. `import` from the menu with an empty answer asks again, with `fail  give the path of an exported box`. **By hand.**
- [ ] The note saves within about a second of stopping typing and on leaving the window, and reloads after `target add` writes to it, with no "file changed" prompt from vim. **By hand.**
- [ ] `.note-state` reads `1` while there are unsaved changes and `0` after a save, and `finish` stops while it reads `1`. **By hand.**
- [ ] The palette shows as the brand hex values, and `NO_COLOR=1 pwn-broker` prints no colour. **By hand.**
- [ ] `cred add` with `p@ss "word" with spaces\` round-trips through `cred show` and `lists/passwords.txt` unchanged. **Kali job:** a plain secret reaches `lists/passwords.txt`. **By hand:** this secret.
- [ ] As a normal user: `sudo nmap -oA` into a target's `scans/`, then `finish`. The archive is written and verified, and the folder can be removed. **By hand.**
- [ ] `sudo /opt/pwn-broker/bin/pwn-broker` as the normal user refuses to start and names the user (the full path, because `sudo` does not search the user's PATH). **By hand.**
- [ ] `export`, copy the file to a second VM, `pwn-broker import <file>`: targets, note, creds and flags are all there and the prompt opens on the last target. **Kali job:** `import` of a finished archive in the same container brings back the folder, the `/etc/hosts` line and the tool. **By hand:** on a second VM, and the note, creds and flags.
- [ ] A second `pwn-broker` in another terminal, while a box is open, refuses and names the open box. **By hand.**
- [ ] At a question, Ctrl-C cancels that command and returns to the prompt. Ctrl-D at the prompt offers the export and quits. **By hand.**
- [ ] With the note open in vim, change `notes.md` from another terminal (`echo x >> notes.md`). Vim shows the change within about a second, and `.note-state` in the box folder still reads `0`. **By hand.**
- [ ] Type in the note, then within a second run `target add` in the prompt. Vim does not show a "file changed" prompt, and nothing typed is lost. **By hand.**
- [ ] The note opens with every target fold closed, each showing only its `Target:` line. **By hand.**
- [ ] A closed fold is drawn on the raised colour (`#1A1D24`) across the whole line. **By hand.**
- [ ] IP addresses are Amber and `<Placeholder>` text is Ember, inside the box at the top as well as below it. **By hand.**
- [ ] `F8`, in normal mode and in insert mode, adds an empty fold below the line, open, with the cursor on its blank line in insert mode. **By hand.**
- [ ] Open a fold, put the cursor inside it, then run `target add` in the prompt. After vim reloads, that fold is still open, the others are still closed, and the cursor is on the same text. **By hand.**
- [ ] Select some lines in visual mode in the note, then run `target add` in the prompt. The selection stays until you leave visual mode, and the note reloads after that. **By hand.**
- [ ] While the note is open, no `.swp`, `~` or other backup file appears in the box folder. **By hand.**
- [ ] The status bar is muted text on the normal background, not reverse video, and its clock moves while the prompt is idle. **By hand.**
- [ ] The completion menu opens while typing a command, and Tab completes target names. **By hand.**
- [ ] As a normal user, `/opt/pwn-broker` belongs to that user after install, and `pwn-broker` runs without `sudo`. **By hand.**

## Tools

The packages are published in `pwn-shop`. With no `tools_index` setting the tool commands read its published index, which has been tried on Kali by hand under WSL, as root for all six tools and as a normal user for three: do the steps below once that way. CI does them from a folder. Get one in a clone of `pwn-shop`: `sh fetch.sh <folder>` downloads the published index and zips with `curl`, or `python build.py build` builds them into `dist/`. Either way the folder holds `index.toml` and the zips it names. Set `tools_index = "<folder>"` in `/opt/pwn-broker/config.toml`. Build 3 of `certipy` and `targetedkerberoast` and the `python-3.13` runtime are published and in the index, so `fetch.sh` brings them with the rest: run against the real releases on Kali on 2026-11-16, as a normal user, it downloaded all seven zips and each matched the index.

- [ ] The install does not depend on Kali's Python. On a fresh Kali, the installer runs to its last line with the network off, and `/opt/pwn-broker/app/bin/python` resolves to `/opt/pwn-broker/python/bin/python3.13` whatever `python3 --version` says. There is no `python3-venv` check any more. **Kali job:** covered, as root: the app's Python was 3.13.18 while Kali 2026.3's own was 3.14.10, and `.zshrc` held Kali's own lines plus one PATH line. CI's `installer` job also installs it in a Debian container with no Python at all. **By hand:** a fresh Kali VM, as a normal user, with the installer's own `sudo` step. An upgrade over an install made by the old installer has run by hand, as root under WSL (see [tested.md](tested.md#an-upgrade-from-the-old-installer)).
- [ ] With `tools_index` set to the folder, `tool list` shows the six packages (kerbrute, pspy, certipy, targetedkerberoast, ligolo-ng, peass-ng) and a `kali` column. `tool refresh` prints `ok` and a count of six tools. With `tools_index` pointing at an empty folder, every `tool` command prints one `fail` line that names the folder and `tools_index`. **Kali job:** `tool list` from a folder index, with one test package. **By hand:** the six packages, `tool refresh` and the empty folder.
- [ ] `tool install` each of the six in a box. Each prints `ok`, then how to run it. Where Kali already has a command of the same name, a `warn` line gives Kali's path and says the installed one wins. Kali is believed to package `pspy`, `certipy-ad`, `ligolo-ng` and `peass` (its names for them); confirm that, and which command names each installs, and note which installs produced a `warn` line. With Kali's `ligolo-ng` installed, installing ligolo-ng is expected to print a `warn` line that Kali has `ligolo-proxy`, and a second one that `sudo ligolo-proxy` runs Kali's copy and to use `sudo /opt/pwn-broker/bin/ligolo-proxy`. **By hand.**
- [ ] Run each command once from a new terminal: `kerbrute`, `certipy`, `targetedKerberoast`, `ligolo-proxy`. Each starts. The upload files are in `/opt/pwn-broker/upload/<tool>/`. **Kali job:** the test package's command runs from a plain shell. **By hand:** the six.
- [ ] `sudo /opt/pwn-broker/bin/ligolo-proxy`, the path `tool install` and `tool info` printed, starts the installed one. With Kali's `ligolo-ng` installed, a bare `sudo ligolo-proxy` starts Kali's copy; without it, a bare `sudo ligolo-proxy` is not found. `/etc/sudoers` is unchanged. **By hand.**
- [ ] For any command the check above found Kali already has, Kali's copy still runs as before when called by its full path, and `tool remove` on the installed one makes the bare name run Kali's again. **By hand.**
- [ ] Note what `ligolo-proxy` writes, and where, on its first run, both ways: run as you, and under `sudo`, where the home folder is root's. The package's data paths depend on it. **By hand.**
- [ ] Open a second box and `tool install` the same tool: the same build shares it. A different build stops and names the first box. **By hand.**
- [ ] While `ligolo-proxy` is running, `finish` and `tool remove ligolo-ng` both stop and name it. **By hand.**
- [ ] `finish` lists the box's tools and every path under the home folder it will delete. Afterwards no command, no upload folder, no `tools/` folder and no tool data from that box is left, and a path that existed before the install is still there with a `warn` line about it. **Kali job:** the summary lists the test package, and afterwards its command and `tools/` folder are gone. **By hand:** a tool with home data, and a path that existed before.
- [ ] `tool install certipy` (build 3, which requires `python-3.13`) on a machine with no runtime prints `ok    python-3.13 3.13.18 installed (runtime, <n> MB)`, then `ok    certipy 5.1.0 installed`. `certipy --help` runs, and `/opt/pwn-broker/tools/certipy/5.1.0-3/venv/bin/python -c 'import sys; print(sys.version_info[:2], sys.base_prefix)'` gives `(3, 13)` and a folder under `/opt/pwn-broker/tools/python-3.13/`, while `python3 --version` is still Kali's own. `tool list` does not show `python-3.13`, `tool info certipy` has a `requires` line for it, and nothing named `python*` appears in `/opt/pwn-broker/bin`. Then `tool install targetedkerberoast`: it uses the same runtime and prints no runtime line. **Kali job:** covered, with a Python test tool on a test runtime package around the pinned upstream build: the two install lines (`ok    python-3.13 3.13.18 installed (runtime, 34 MB)` first), the command, `tool list`, `tool info` before the install, and nothing in `/opt/pwn-broker/bin`. Kali's own `python3` was 3.14, and the tool's environment was Python 3.13 with its base at `/opt/pwn-broker/tools/python-3.13/3.13.18-1/root/python`. **By hand:** build 3 of `certipy` and `targetedkerberoast`, and a second tool sharing the runtime.
- [ ] `finish` lists `runtimes  python-3.13 3.13.18   (will be removed)` in its summary, and after the archive prints `ok    python-3.13 3.13.18 removed (runtime)`. Afterwards `/opt/pwn-broker/tools` holds nothing but `installed.toml`. `import` of the finished archive installs the runtime again before the tool. With two unfinished boxes that use tools on the runtime, finishing one leaves the runtime in place. **Kali job:** covered: the summary line, the removal, the empty `tools` folder, and the runtime coming back with the tool at `import`. **By hand:** two boxes sharing the runtime.
- [ ] `tool history` lists every tool the box has had, with its install time, its removal time or `-`, and the runtime it ran on. After `tool remove`, the tool stays in the list with a removal time. `~/pwn-broker/tools.log` has mode 600 and a line for each install, `tool remove` and `finish`, a runtime's lines ending in `runtime`. **Kali job:** covered: `tool history` with two tools, one on the runtime, the runtime recorded with the tool in `box.toml`, the log's mode, and its `install` and `finish` lines for both tools and the runtime, at the first install, `finish`, `import` and the last `finish`. **By hand:** `tool remove` and its `remove` lines.
- [ ] `export` copies tool data into the box and removes nothing. `pwn-broker import <file>` on a fresh VM offers to install the tools again, and the same builds come back. **Kali job:** `import` offers to install the test package again, and it comes back. **By hand:** tool data, and a fresh VM.

## Recording, /etc/hosts, the VPN and the ping

The Kali job has run most of this as root; what is left is marked. Work through it in one box, once as root and once as a normal user, with a Hack The Box `.ovpn` file to hand. Before you start, copy `/etc/hosts` aside (`cp /etc/hosts /tmp/hosts.before`) to compare with afterwards.

- [ ] After the install, the installer prints `ok    asciinema 3.2.1 in /opt/pwn-broker/app/bin/asciinema` (from `setup`, which fails if the copy in the release file is missing or does not match its pin; nothing is downloaded), and `/opt/pwn-broker/app/bin/asciinema --version` prints 3.2.1. `check` in the prompt shows no `asciinema` line, because it passed. `which asciinema` does not name the app's copy. **Kali job:** covered, except `which asciinema`.
- [ ] In a second terminal, with the box open in the prompt, `record` prints `ok    recording this window for <target> (<box>)` and the path of the `.cast`. Run `ls -l` on that `.cast` from a third terminal a few times while typing commands in the recorded one: its size grows as you work, not only at the end. **Kali job:** covered; the growing `.cast` is checked by the real-asciinema tests in the unit suite.
- [ ] With Kali's own zsh settings (a fresh `~/.zshrc` from Kali), the recorded window's prompt starts with `[rec <target>]`, and the rest of the prompt, the colours, the suggestions, the aliases and the history behave as they do outside `record`. Do the same with `SHELL=/bin/bash record` and Kali's own `~/.bashrc`. **Kali job:** the prefix in front of Kali's own two-line prompt, from root's `.zshrc` as Kali ships it. **By hand:** the colours, suggestions, aliases and history, and bash with Kali's `~/.bashrc`.
- [ ] Press Ctrl-P in the recorded zsh window, Kali's toggle between its one-line and two-line prompts, then Ctrl-P again. Note whether the `[rec <target>]` prefix stays, or is gone until the next command is run. **By hand.**
- [ ] In the recorded window, run `nmap` against a target, type a command and edit it before Enter, run a command whose output wraps (a long hash), open `vim` and quit it, and press Ctrl-L once. `exit`, then open the `.txt`: each command reads as typed, with zsh's suggestions and highlighting gone, an edited command appears once as it was run, the wrapped line is one line, vim is one `[full-screen program until ..., see the cast]` line, and every line of text starts with a time. **Kali job:** a timed line for one command's output. **By hand:** the rest.
- [ ] `replay` in the prompt lists the recording with its start time, length and size. While a second window is recording, it shows `recording now`, and `status` shows `recordings` with `(1 recording now)` and the status bar `rec 1`. `finish` refuses and names the target. `export` warns, and the export holds the recording up to that moment. **Kali job:** the list, `status` with `(1 recording now)`, `finish` refusing and naming the target, and `export` warning and holding the recording. **By hand:** `recording now` in the list and `rec 1` in the status bar.
- [ ] `replay 1` plays the recording in the prompt window, with idle gaps cut to two seconds. Space pauses. Press Ctrl-C part way through: it returns to the prompt. Note whether the app prints `warn  asciinema ended with status <n>`, and with which status, and whether the terminal is left as it was, with the cursor shown, echo on, and the prompt working normally. **Kali job:** it plays to the end, the prompt comes back and takes a command, and no status warning is printed. **By hand:** Space, Ctrl-C and the terminal's state after.
- [ ] `sudo /opt/pwn-broker/bin/record` as the normal user (the full path, because `sudo` does not search the user's PATH) refuses and says to run `record` first, then `sudo` inside it. **By hand.**
- [ ] `target add` with an IP and a hostname asks `add <target>'s hostnames to /etc/hosts? [Y/n]`. Press Enter. As root the line is written directly; as a normal user `sudo` asks for the password once. The new line ends with `# pwn-broker <box ID>`, `getent hosts <hostname>` gives the IP, and `diff /tmp/hosts.before /etc/hosts` shows only that line. `ls -l /etc/hosts` shows the same owner and mode as before, and `ls -i` the same inode. **Kali job:** as root, from the new-box questions: the line, its mark, `getent` and every other byte unchanged. **By hand:** `sudo` as a normal user, and the owner, mode and inode.
- [ ] That new target is pinged once: `ok    <ip> answered in <n> ms`, or `warn  <ip> did not answer a ping; Windows targets often do not`. Ctrl-C during the two-second wait prints `cancelled` and nothing else is skipped. **Kali job:** the `answered in` line. **By hand:** Ctrl-C.
- [ ] `host add <name>` rewrites the line without asking, and `host` shows every hostname with `yes` under `in /etc/hosts`. `host file off` takes the line out, and the file matches `/tmp/hosts.before` again. **Kali job:** `host add` and `host`. **By hand:** `host file off`.
- [ ] As a normal user, run `sudo -k`, then `host file on` for a target with no line, and type a wrong password at each of `sudo`'s three tries. Nothing in `/etc/hosts` changes, and the app prints a `warn` line and the line to add yourself. **By hand.**
- [ ] `host file on <target>` again, typing the right password this time, then `quit` the prompt. The box's line stays in `/etc/hosts`, and `getent hosts <hostname>` still answers. Launch `pwn-broker` again with no VPN up. The launch checks print `warn  vpn   no VPN tunnel is up` and `start one with: vpn start`, and the app still starts. Resume the box. The status bar shows `no vpn`. **Kali job:** the line stays after `quit`, and each later launch prints the `vpn` warn line and still starts. **By hand:** `host file on` with `sudo`, and the status bar.
- [ ] `vpn start` with the Hack The Box file: the question takes the path with Tab completing it, the file is copied to `vpn/` in the box with mode 600 (`ls -l`), and the app prints `ok    vpn up, <address> on tun0`. Note the interface name if it is not `tun0`. The status bar shows `vpn <address>`. **Kali job:** with a file that has no server: the copy with mode 600 and `ok    vpn up, 10.10.14.7 on tun0`. **By hand:** a Hack The Box file, Tab completion and the status bar.
- [ ] With a file that asks for a username and password (`auth-user-pass` with no file named), OpenVPN asks for them in the prompt window before it goes to the background, and the tunnel comes up. **By hand.**
- [ ] Close every terminal window except the prompt, then `quit` the prompt. From a new terminal, `ip -4 addr show tun0` still shows the address. Open the box again: `vpn status` shows `up`, the file and the box that started it, and `vpn log` shows OpenVPN's log. **Kali job:** OpenVPN's parent is PID 1 and it has no controlling terminal, and `vpn status` and `vpn log` print. **By hand:** quitting the prompt with the tunnel up and opening the box again.
- [ ] `vpn stop` prints `ok    vpn stopped`, and `ip addr show tun0` no longer finds the interface. Start one by hand with `sudo openvpn --config <file>` in another terminal: `vpn stop` refuses and says to stop it yourself, and it is still up afterwards. Stop it with Ctrl-C in its own terminal. **Kali job:** the line, and no OpenVPN or `tun0` left. **By hand:** a tunnel started by hand.
- [ ] `vpn start` again, then `finish`. The summary includes a `hosts` row, `1 line to remove from /etc/hosts`. After the archive is written it prints `ok    removed 1 line from /etc/hosts`, and `cmp /tmp/hosts.before /etc/hosts` finds no difference (Kali's file ends with a line break; one that did not would gain one). It then asks `the VPN is still up (<address>). stop it? [y/N]`; Enter keeps it up, and `ip -4 addr show tun0` still shows the address. `tar -tzf` on the archive lists no `vpn/` entry. **Kali job:** covered, answering `y` to the VPN question, after which no OpenVPN or `tun0` is left. **By hand:** Enter keeping it up.
